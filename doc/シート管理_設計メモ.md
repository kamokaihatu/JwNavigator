# JwNavigator シート管理機能 設計メモ

## 背景・課題
- 問題1: JW-CADはレイヤ名が見えない
- 問題2: レイヤ状態(表示/非表示など)を記憶する機能がない
- 問題3: 必要な状態に一括で切り替える機能がない

→ auto、CADEWA、T-fas、Rebroなどにある「シート管理」機能をJwNavigator側に独自実装したい。

## スコープ(2機能セット)
JW-CAD上でレイヤに名前を付ける操作自体が手間なため、シート管理だけでなく「レイヤ名の管理」もJwNavigator側で行う。

1. **レイヤ名簿**: レイヤ番号(0〜F)×名前 の対応表。JW-CADのファイル形式(jww)にレイヤ名を保存できるかは未検証のため、JwNavigator側で独自に対応表を保持する想定。
2. **シート表**: シート名×対象グループ(0〜9)×各レイヤの表示/非表示状態(下記データモデル参照)。レイヤ名簿で付けた名前を使って表示する。

保存形式(JSON/SQLite/xlsxなど)は「見やすさ・操作しやすさ」を優先して実装時に決定。エクセルの表2枚(レイヤ名簿・シート表)のようなイメージで、JwNavigatorのパネル上で編集・一括切替できるようにする。

## 現状の前提(要検証事項含む)
- JW-CADには公式API/DLLは存在しない
- 連携手段の候補は以下の2つ
  1. **外部変形**: Jw_cad公式の拡張機構。選択データをテキストで受け渡す仕組み。グループ全体の一括切替には不向き。
  2. **レイヤ一覧バー(画面下部)への文字列入力**: レイヤグループ切替に使われる公式の操作方法。UI自動化(キー入力送信 or ウィンドウメッセージ送信)で操作できる可能性が高い。
- JWWファイルの直接バイナリ編集は破損リスクが高く、即時切替体験に向かないため非推奨

**⚠️ 要検証**: レイヤバーへの入力書式(グループ番号+レイヤ表示パターンの具体的な文字列仕様)は、Jw_cadのバージョン・設定に依存する可能性がある。実装前にJw_cad公式ヘルプ、または既存の自動化事例(AutoHotkeyスクリプトなど)を調査して仕様を確定させること。

## 方式比較

| 方式 | メリット | デメリット | 判定 |
|---|---|---|---|
| JWWバイナリ直接編集 | 精密な制御が可能 | 破損リスク、再読込が必要、即時性に欠ける | 非推奨 |
| 外部変形 | 公式機構で安全 | グループ一括切替に不向き | 補助的に利用 |
| レイヤバーへの文字列送信(UI自動化) | グループ切替含め一括操作可能 | フォーカス/バージョン差異に弱い | 有力候補(要検証) |

## データモデル(案)

```
Sheet {
  id: string
  name: string              // シート名(例: "基礎伏図", "配線図")
  description: string
  target_group: int         // 対象レイヤグループ (0-9)
  layer_states: dict         // { layer_no(0-F): visible(bool) }
  created_at: datetime
  updated_at: datetime
}
```

## JwNavigator側UI(パネル案)
- シート一覧表示(登録済みシートをリスト表示、レイヤ名が見える化される)
- 「現在の状態を新規シートとして保存」ボタン
  - ※現状のレイヤ状態の取得方法は未検証(要検証事項参照)
- 「適用」ボタン: 選択したシートの状態をJw_cadに一括反映(レイヤバーへ文字列送信)
- 編集・削除・並べ替え

### 個別レイヤ操作(シートとは別機能)
シート(複数レイヤの一括切替)とは別に、レイヤ1本ずつを素早く操作したいニーズがある。

- 対象: レイヤごとの「表示/非表示」「選択可/選択不可(編集保護)」
- レイヤ名簿の一覧上で、各レイヤ行にワンクリックのトグルボタンを置くイメージ
- シート適用(グループ一括切替)とは独立した操作として、いつでも個別に呼び出せるようにする

## 2026-08-27 実機調査で判明したこと

「補助線」自動化コマンドの調査（レイヤ・線属性を自動設定→直線コマンドへ切替→他コマンドに切り替わったら元に戻す）から派生して、jw_cadのレイヤ操作まわりの内部構造をかなり詳しく調べられた。

### レイヤ/グループの直接操作（画面右下のツールバー）

jw_cad本体ウィンドウの子ウィンドウとして、「レイヤ」「レイヤグループ」という`ToolbarWindow32`が実在し、それぞれ実際の`Button`コントロール16個（0〜F、左列0-7・右列8-F、上から順）を持つことを確認（`EnumChildWindows`で列挙可能）。

- **グループ/レイヤの切替**: 対象ボタンへ`WM_RBUTTONDOWN`+`WM_RBUTTONUP`（右クリック相当）を送ると、そのグループ/レイヤが入力（書込み）対象になる。左クリック(`BM_CLICK`)は別機能で、そのレイヤの表示状態を「編集可→非表示→表示→編集可→…」と3状態循環させるだけ（入力レイヤにはならない）。
- **現在の入力レイヤ判定**: `BM_GETSTATE`（0x00F2）で押し込み状態(`BST_PUSHED`=0x4)になっているボタンを16個から探せば、現在どのレイヤが入力状態か分かる。ポインタを使わない安全な整数メッセージ。
- **入力から外れた時の挙動**: 入力レイヤを別のレイヤに切り替えると、元々入力だったレイヤは自動的に「編集可」状態に落ち着くことを実測で確認（同じ数字の色パターンが「編集可」時と完全一致）。つまり「切替前がどのグループ/レイヤだったか（番号）」さえ覚えておけば、戻す時は右クリックし直すだけで正しく復元される。
- **編集可/表示/非表示の3状態の見分け方**: `BM_GETCHECK`/`BM_GETSTATE`では区別できない（全部0x0）。ボタン領域のピクセル色を`GetPixel`でサンプリングし、黒ピクセル数などのパターンで判別できる可能性があるが、数字の形自体に依存するため、対象レイヤ番号ごとに一度キャリブレーション（既知の3状態を作ってパターンを記録）する方式が現実的。

### 線属性（色・線種・太さ）ダイアログ

idCommand=32807（`線属性`、C047）で開く「線属性」ダイアログは通常のWin32ダイアログで、線色1〜8+補助線色（9個のボタン）、線種9個（実線〜二点鎖2+補助線種）、線幅入力欄(`Edit`)、Ok/キャンセルボタンが全て個別の子コントロールとして取得できる。**「補助線色」「補助線種」はjw_cad自体に用意された既定プリセット**であり、`BM_CLICK`で選択→線幅欄を`WM_SETTEXT`で設定→OKボタンを`BM_CLICK`、という一連の操作で確定できることを実機で確認済み（自動化で線属性を補助線色/補助線種に変更→OK→反映を確認）。

⚠️ このダイアログの子コントロールのhwndは**ダイアログを開き直すたびに変わる**ため、ハードコードせず毎回`EnumWindows`でタイトル「線属性」から探し、`EnumChildWindows`で子を列挙し直す必要がある。

## 2026-09-03 実機調査で判明したこと(レイヤ名・状態の読み取り)

「レイヤー管理」プロジェクト着手にあたり、調査フェーズ(現在のレイヤ状態の取得方法の検証)を実施。

⚠️ **このセクション全体の位置づけ**: 長時間の実機での差分実験の記録であり、特に「図面情報をコピー」のビットエンコーディング解析部分は終盤ほど検証が粗くなっている(複合変更・矛盾する結果を含む)。**次回はこのセクションを鵜呑みにせず、参考情報としつつも重要な部分(特にビット位置の仮説)はゼロから検証し直すこと。** 一方、「レイヤ名はステータスバーで読める」「レイヤ/グループの右クリック切替は合成メッセージで可能」といった前半の確定事項は、既存コード(`utils/line_attr_dialog.py`)と整合しており信頼度が高い。

### レイヤ名の読み取り: ステータスバーで完全に解決

ステータスバー(`msctls_statusbar32`)のパート3(`SB_GETTEXTW`、`utils/line_attr_dialog.py`の`_read_statusbar_part`と同じ手法)には、`[グループ-レイヤ]レイヤ名`という形式でレイヤ名がそのまま入っている。

- 例: `[0-6]010扉` → グループ0・レイヤ6・レイヤ名「010扉」
- 名前が未登録のレイヤは`[G-L]`のみ(名前部分が空)。**無題(空)ファイルで最初に試した時に名前が全く出てこず「取得不能」と誤診断した**が、単に名前が登録されていないだけだった(既存の実ファイルで再検証して判明)。
- 既存の`read_current_layer_group()`の正規表現(`\[([0-9A-Fa-f])-([0-9A-Fa-f])\]`のみキャプチャ)を拡張し、`]`の後ろの残り文字列をレイヤ名として読めばよい。追加のダイアログ自動化は一切不要。
- ⚠️ **この方法で読めるのは「今アクティブなグループの、今アクティブなレイヤ」の名前だけ**。他グループ/他レイヤの名前を読むには、そのレイヤを一旦アクティブにする(右クリックで切替)必要がある＝全256レイヤを読むには16グループ分の切替走査が必要になる。

### 「レイヤ一覧」ダイアログ(右クリックで開く方の管理画面)

- 選択中のグループ/レイヤボタンを**物理的に(実マウスで)右クリック**すると、「レイヤ一覧　( [グループ番号] グループ )」という`#32770`ダイアログが開く。タイトルは開いた時点のアクティブグループが入る。
- ⚠️ **合成右クリック(`WM_RBUTTONDOWN`/`UP`をPostMessageで送る)ではこのダイアログは開かない**。レイヤ/グループ切替自体は合成右クリックで機能するが、この一覧ダイアログの表示は実機の物理マウス操作でないとトリガーされない模様(実機で複数回確認)。同様に、ダイアログ内の「リスト表示」ボタンへの合成`BM_CLICK`も無反応だった。
- ダイアログの中身: 16個のレイヤは独自描画(owner-draw)の`Afx:...`コントロール(アクセシビリティ名は"ファイル選択"という汎用文字列で、実際の描画内容とは無関係)で、`GetWindowText`では中身が読めない。`SysTreeView32`/`SysListView32`も存在するが、「リスト表示」ボタンが無効化されている状態では空(0件)。もう一つのグループを開いた状態や、別の起動経路があれば有効化される可能性はあるが未検証。
- この経路は**現状、自動化での読み取りには使えていない**。

### レイヤボタンのピクセルによる3状態判別(編集可/表示/非表示)

メイン画面下部のレイヤバー(16個の`Button`、`utils/line_attr_dialog.py`の`_find_layer_group_buttons`で取得済み)を`GetPixel`で読み取ることで、編集可/表示/非表示を判別できる可能性を実機で確認。

- ⚠️ **必須の前提条件が2つ**:
  1. **DPI awareness**: `main.py`と同様に`ctypes.windll.shcore.SetProcessDpiAwareness(2)`を呼んでおかないと、`GetWindowRect`の座標と実際の物理ピクセル座標がズレて、全く違う場所を読んでしまう(実機で「全ボタンが同じ色になる」という誤った結果が出て原因究明に時間がかかった)。
  2. **Z順**: 対象ウィンドウ(jw_cad本体)を一時的に`HWND_TOPMOST`にしてから読む(既存の線属性ダイアログ読み取りと同じ理由)。他のウィンドウ(このセッションではClaude自身のウィンドウ)が偶然レイヤバーの真上に重なっていて、最初は全部その背景色を読んでしまっていた。さらに、topmost化は一瞬しか有効でないことがあり(裏に回ってしまう)、16個全部を読み切る前に失敗するケースがあった。ウィンドウが最小化されている場合は`GetWindowRect`が`(-32000, -32000)`付近の異常値を返すので、`IsIconic()`で事前チェックすべき。
- ❌ **「黒ピクセルの合計数」で状態判定するのは不可**(ユーザー指摘: 「ピクセルで数えると良くないと思う。記入された状況で変わってくる」)。レイヤに描画されている内容によって左上/右上に別の印(データ有無マーク、文字系かどうか)が出るため、単純な合計はそれと混同する。
- ✅ **有効そうな特徴**: 数字グリフの描画される「縦方向の範囲(行数)」で判別できそう。
  - **非表示**: 数字が一切描画されない(該当領域が完全に空白)
  - **編集可**(および現在の入力レイヤ): 数字がフル高さ(ボタン領域の縦幅いっぱい、実測で約17行中3〜19行目)で描画される
  - **表示のみ(編集不可)**: 数字が小さく、中央付近の一部の行だけに縮こまって描画される(実測で約17行中7〜15行目程度)
  - **入力中(現在アクティブ)**: 編集可と同じフル高さの数字に加えて、ボタン左端に縦一列の印(バー)が追加される
  - 8個のground truthで完全一致を確認済み。ただし本格実装する場合は、数字の形状自体に依存しない「行ごとの黒画素の有無パターン」を都度キャリブレーションする方式が安全(調査メモの2026-08-27時点の記述と同じ結論)。

### 「図面情報をコピー」機能とレイヤ状態のビットエンコーディング(最有力候補)

jw_cadのファイルメニューにある「図面情報をクリップボードにコピー」を実行すると、クリップボードに以下のような1行のコマンドライン形式文字列が入る:

```
{ファイルフルパス} -M -P0,0,1,0,0 -LP0200?ooP00800@0100400@0100400@0100400@010040?oooon00800ooooooooool40?ooooooooooooooooooool
```

- `-P0,0,1,0,0`: 恐らく現在の表示位置/縮尺等(未検証)。
- `-LP...`(または状態によっては`-Ll...`): **レイヤ状態を表すエンコード文字列**とみられる。90文字前後、使用文字種は`0-9`, `?`, `o`, `l`, `P`, `@`, `^`, `R`, `_`, `g`, `W`など。
- **実機での差分実験で判明した確定事項**:
  - この文字列の**1文字が複数レイヤの状態をビット単位でまとめてエンコード**している(単純な「1レイヤ=1文字を並べる」方式ではない)。
  - グループ0のレイヤ1・レイヤ2が、文字列中のある1文字(実験当時の位置で45文字目、`-L`を除いた文字列先頭からのオフセット)に、以下のようなXOR関係で載っていることを確認:
    - 基準(両レイヤとも編集可): `o` (0x6F)
    - レイヤ1のみ非表示: `_` (0x6F ^ 0x30)
    - レイヤ2のみ非表示: `g` (0x6F ^ 0x08)
    - 両方非表示: `W` (0x6F ^ 0x38、0x30と0x08の論理和と一致)
  - この特定のビット(0x30側)は、「非表示」と「表示のみ(編集不可)」の**両方で同じ値になる**(どちらも「編集可ではない」状態)。つまりこのビットは「編集可否」フラグで、「表示するかどうか」は別の場所に独立したフラグとして存在する。
  - **「表示のみ」フラグの位置を特定**: `-LP0`の直後から、レイヤごとに1文字ずつ並んでいるとみられる。
    - レイヤ1(グループ0内)が「表示のみ」の時だけ、位置4の文字が`2`→`3`に変化(編集可・非表示では`2`のまま不変)。
    - レイヤ2が「表示のみ」の時だけ、位置5の文字が`0`→`P`に変化(編集可・非表示では`0`のまま不変)。
    - つまり `-LP0[レイヤ1の表示フラグ文字][レイヤ2の表示フラグ文字]...` という並びの可能性が高い。ただし各位置の「基準値」(`2`や`0`)が異なっており、単純な共通アルファベットではなく位置ごとに意味/範囲を持つ値の可能性がある(未確定)。
- **未解決事項の続き、および「全部/多くを非表示にする」実験で判明した追加の構造**:
  - グループ0のレイヤをいくつか動かした状態から、「可能な限り非表示にした」ところ、`-L`以降の文字列の**形そのものが一変**した(`-LP0200?ooP00800@...`のような形から、`-L00600800P0200800P0200800...`のような、8文字ブロックが大量に繰り返される形に変化)。全体の長さは93文字で以前と一致していた(偶然の可能性もあり未確定)。
  - `-L`を除いた本体を8文字ずつに区切ると、ほとんどのブロックが同じ`P0200800`(「グループ全レイヤ非表示」の型とみられる)で、**1箇所だけ違うブロック**(例: `P0200001`)があった。
  - その「1箇所だけ違うブロック」が何を指すかを実験したところ、**グループ番号に固定されたものではなく、「今アクティブなグループ」を指す特別スロットらしい**ことが判明:
    - グループ0を編集していた時はそのブロックがグループ0の状態を反映し、その後グループFのレイヤ(F-F)を編集したら、**同じブロック位置**がグループFの状態を反映するように切り替わった。
    - ブロック内でも位置による意味の違いを確認: ブロック先頭寄り(位置44)が**レイヤ0**、ブロック後ろ寄り(位置47)が**レイヤF**に対応する変化を見せた(F-0が入力→編集可になった時は位置44、F-Fが編集可→入力になった時は位置47が変化)。ブロック内でレイヤ0〜Fが先頭から順に並んでいる可能性が高い。
    - つまり全体構造の仮説: 「`-L` + ヘッダ的な数バイト + [アクティブグループの詳細ブロック] + [その他グループ(非アクティブ)の圧縮された繰り返しブロック]」というような、**アクティブグループを特別扱いする構造**である可能性が高い。単純な「グループ0から順に16ブロック並べる」ではない。

**重要な確認事項**:
- **文字列の総長は常に93文字**(白紙ファイルでも、大量に編集したファイルでも)。これは偶然ではなく**固定長フォーマット**であることをほぼ確信できる(圧縮ではなく、決まったサイズの構造体をそのままテキスト化したもの、後半の`o`の連続はデータが無い部分の埋め草とみられる)。
- グループ切替(0→1)は`-L`の直後、**位置0の1文字だけ**が変化(`P`→`@`)。白紙ファイルというノイズの無い条件でこれだけ綺麗に1文字だけ変わったのは大きな収穫。
- グループ7への切替では、**位置0ではなく位置1**が変化(`0`→`@`)、位置0は基準の`P`ではなく`0`になっていた。
- 上記から、アクティブグループ番号は「位置0・位置1の2文字にまたがって、ビット単位で分散してエンコードされている」可能性が高い(例: グループ7=2進数`0111`なら、下位2ビットが位置0に、残りのビットが位置1に、というような分割)。単純に「1文字=そのままの16進数字」ではなさそうだが、値の変化量が`0x50→0x40→0x30`のように**常に0x10刻み**になっているのは良い手がかり。
- **次回はこの白紙ファイルを使い、グループ0〜Fを1つずつ順番に試して、位置0・1の値を全パターン記録すれば、アクティブグループ番号のエンコードは確実に解読できる見込み。**

この操作では末尾付近の位置90のみが変化(`P`→`0`)。文字列の一番後ろの方(グループFはグループ番号順で最後とみられる)に、非アクティブなグループFの詳細が圧縮された形で存在し、そのレイヤ0部分がここに対応しているとみられる。

最後の操作(グループFを丸ごと非表示)では位置49のみが変化(`1`→`0`)。アクティブグループ(8)の詳細ブロックのすぐ後ろ、非アクティブグループ群の圧縮ブロックの先頭付近とみられ、「グループ単位の圧縮表現」が1文字程度の粒度で変化しうることを示している。

**重要な追加発見**: グループF→8への切替では、位置3の文字が`0`→`8`に変化した。**これはアクティブなグループ番号(16進数1桁)がそのまま書かれている可能性が高い**(グループ8に切り替えたら literally `8`になった)。これにより「特別スロットに、アクティブグループの詳細が入る」という仮説の裏付けが取れた。全体像はおおよそ:

```
-L [?] [アクティブグループ番号(16進1桁)] [ヘッダ的な数バイト] [アクティブグループの16レイヤ詳細] [他グループの圧縮された繰り返しブロック...] [末尾1〜数文字(チェックサム？)]
```

という構造の可能性が高い。ヘッダのグループ番号さえ読めれば「今読み取れているのはどのグループの詳細か」が確実に分かるので、これを起点に**16グループを1つずつアクティブにしながら記録していけば、全256レイヤの状態を(切替を伴うが)確実に読み取れる**という現実的な実装方針が立てられる(これは元々検討していた「グループを巡回する」方式そのものだが、今回の解析でこの方式の実装に必要な情報(各グループのアクティブ時の詳細ブロックの正確な読み方)が揃ってきた)。

**現在の設定値の読み取りも可能**: レイヤ/グループの入力状態判定と全く同じ`BM_GETSTATE`（0x00F2、`BST_PUSHED`=0x4）が、線色9個・線種9個のボタンでも「現在選択中」を正確に示すことを実機で確認（線色2番目・実線が選択中の状態で、それぞれのボタンだけ0x4を返した）。線幅は`Edit`欄を`WM_GETTEXT`で読める（安全・標準）。つまり「補助線」機能に必要な「元の線属性を覚えておく」は、ダイアログを開いて9+9個のボタンを`BM_GETSTATE`で走査し幅欄を読み、変更せず**キャンセル**で閉じる、という手順で実現できる。読み取り後にダイアログを開いたままにせず確実にキャンセルすること（OKだと反映されてしまう）。

### レイヤ設定ダイアログ（グループ名・レイヤ名の読み書き）

layer bar をダブルクリック等で開く「レイヤ設定」ダイアログには、グループ名・レイヤ名それぞれの**編集可能な`ComboBox`+`Edit`**が存在する。これは名前を`WM_SETTEXT`で書き込み・`WM_GETTEXT`で読み取りできる、標準的で安全なコントロール（クロスプロセスでも自動マーシャリングされるため安全）。実機で「レイヤ0」に名前を設定→OK→保存されることを確認済み。**問題1「レイヤ名が見えない」への直接の解決策になる。**

### ステータスバーの複数パート読み取り（重要な安全上の教訓あり）

jw_cadのステータスバー（`msctls_statusbar32`）は実は**6パート構成**（`SB_GETPARTS`で確認）で、パート3に`[グループ-レイヤ]レイヤ名`形式の文字列が入っていることを実機で確認（例:`[0-0]テステスト0-0`）。これも「現在のレイヤ名」を読む手段として使える。

- パート0: メインの操作プロンプト（今まで`WM_GETTEXT`で読んでいたのはこれだけ）
- パート1: 座標/角度系表示（例:`A-2`）
- パート2: 縮尺（例:`S=1/50`）
- パート3: `[グループ-レイヤ]レイヤ名`
- パート4/5: その他の表示（未特定）

**⚠️ 重大な注意**: `SB_GETTEXTW`は他の多くのWin32メッセージと違い、クロスプロセスで自動マーシャリングされない。ローカルのバッファポインタをそのまま渡すと相手プロセス（jw_cad）がそのアドレスへ書き込もうとして**実際にjw_cadをクラッシュさせた**（本調査中に1回発生、実害はテスト環境のみで確認済み）。正しくは対象プロセス内に`VirtualAllocEx`でメモリを確保し、そのポインタをメッセージに渡し、結果を`ReadProcessMemory`で読み戻す、という手順が必須。`OpenProcess`/`VirtualAllocEx`の戻り値が0（失敗）の場合は絶対にその後のメッセージ送信へ進んではいけない（今回のクラッシュはまさにここを素通りしてNULLポインタを送ってしまったのが原因と判明）。この一連の安全な実装パターンは今後`utils/`側に共通化しておく価値がある。

## 2026-09-02 レイヤ切替の実機調査(まだ未解決)

「補助線」ボタン(kind="auto_attr")は実装・実機確認済み(線色/線種の自動切替＋直線コマンドへ移動＋他コマンド切替で自動復帰＋押している間は凹み表示、いずれも実機で動作確認済み)。あわせて「レイヤをF-Fへ変更してほしい」という要望が出て、レイヤ切替の自動化を調査したが、**まだ動く方法が見つかっていない**。

### 分かったこと
- 画面右側の「レイヤ」ツールバー(0〜Fの16個)と「レイヤグループ」ツールバー(同じく16個)は、実は**全32個が同じctrl_id(33038)を共有する**ボタン群(owner-draw)。個別の`hwnd`は持つが、`GWL_ID`では区別できない。
- 現在の実際のレイヤ/グループは、ステータスバー(`msctls_statusbar32`)の**パート3**(`SB_GETTEXTW`、要`VirtualAllocEx`のクロスプロセス安全策、既存の設計メモ通り)で`[グループ-レイヤ]レイヤ名`形式の文字列として正確に読める(実機確認済み、読み取りは問題ない)。
- 一方、ボタン上の「現在のレイヤ番号」表示ラベル(hwnd=67592等)は、実機で試した限りプログラム的な操作では更新されない(見た目が当てにならない、必ずステータスバーで確認する必要がある)。

### 試して失敗した方法(すべて実機のステータスバーパート3で検証、変化なしを確認)
1. `BM_CLICK`をボタンhwndへ直接送信 → フォーカスは付くが選択状態(BM_GETSTATE)は変わらない
2. `WM_LBUTTONDOWN`/`WM_LBUTTONUP`をボタンhwndへ直接送信(jw_cadを前面化した上で、`PostMessage`・`SendMessage`両方試した) → 変化なし
3. 実際の物理マウスクリック(`SetCursorPos`+`mouse_event`) → 別ウィンドウ(VS Code)が画面上の同じ位置を覆っていて危険、中断
4. `WM_COMMAND`に`wParam=MAKELONG(33038,0)`・`lParam=対象ボタンのhwnd`を载せてjw_cad本体(メインhwnd)へ送信 → **一見効いたように見えた**(BM_GETSTATEの凹みビットが動いた)が、16個のボタン全部に対して同じ操作をステータスバーで逐一検証したところ、**実際のレイヤは一度も変わらなかった**。最初の1回だけ凹みビットが動いたのも、別要因(おそらくユーザー側の並行操作)による偶然の一致だった可能性が高いと判断(ユーザーへの報告時に訂正済み)。
5. メインメニューを`GetMenu`/`GetSubMenu`で総ざらいしたが(`ctypes.windll.user32.GetMenuStringW`で全項目のテキストを確認)、レイヤ関連のメニュー項目は「設定(&S)」→「レイヤ(&L)」(id=32808)の1つだけで、これは恐らく「レイヤ設定」ダイアログ(グループ名/レイヤ名の編集ダイアログ、既に調査済み)を開くだけのもの。0〜Fを個別に選ぶメニュー項目は存在しない。
