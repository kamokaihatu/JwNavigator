# JwNavigator レイヤ制御 — 調査結果の引き継ぎ

作成: 2026-09-04 / 調査環境: Jw_cad 10.03.3 (C:\jww), Windows 11, Python 3.13

## 1. 何をやろうとしているか

Jw_cad の全レイヤグループ×全レイヤ（16×16＝256）の状態を

- **保存**（現在の状態を丸ごと記録）
- **復元**（記録した状態に戻す）

を、それぞれ数秒でできるようにする。JwNavigator に組み込むのが最終目標。

当初は「レイヤを1つずつ切り替えて画面情報をコピーし、状態を調べる」という
手作業（256×4≒1000回）をしていたが、それは不要になった。

## 4. 確定した仕様

### 4-1. 外部変形バッチの制御行（256レイヤを取るための必須条件）

```
REM #jww     これが無いと外部変形の「ファイル選択」一覧に表示されない
REM #h1      データ選択方式。これが無いと #g1 が効かない
REM #g1      必ず #h* の直後に置く。全レイヤグループ選択
REM #gn      レイヤの状態と名前を書き出す。これが無いと何も出ない
REM #e
```

3条件すべてが揃って初めて256レイヤが出る。実機での検証結果：

| 制御行 | 結果 |
|---|---|
| `#gn` `#g1`（`#h*` なし） | group=1 layer=16 … `#g1` が無効 |
| `#h0` `#g1`（`#gn` なし） | group=0 layer=0 |
| `#h4` `#g1`（`#gn` なし） | group=0 layer=0 |
| `#g1` のみ | group=0 layer=0 |
| `#h1` `#g1`（`#gn` なし） | group=0 layer=0 |
| `#h4` `#g1` `#gn` | group=1 layer=16 … 選択しないと `#g1` 無効 |
| **`#h1` `#g1` `#gn`** | **group=16 layer=256** ✅ |

`#h*` の種類（`JWW_SMPL.BAT` より）:

- `#h0` データ選択をしない、データ書き出し無し
- `#h1` 範囲内のデータのみを選択
- `#h2` 範囲内データ・範囲内外に跨る線データを選択（かすめるだけで当たる）
- `#h3` 範囲内の「文字」データのみを選択
- `#h4` データ選択をしない、読取可能データ書き出し

### 4-2. 書き出しデータ（`jwc_temp.txt`）の形式

`C:\jww\jwc_temp.txt` に出る（バッチのフォルダではない）。文字コードは Shift_JIS。

```
hq
...ヘッダ...
lgf          ← 値なし = 書込レイヤグループ
ly0          ← 値なし = 書込レイヤ
...
#
...選択された図形データ...
#
lg0 11       ← レイヤグループ0の状態
lgn          ← グループ名（空）
ly0 11       ← レイヤ0の状態
lyn          ← レイヤ名（空）
ly1 01
lyn
...（16グループ×16レイヤ）
```

### 4-3. 状態値の定義（`JWW_SMPL.BAT` より）

`ly%x %d` / `lg%x %d` の `%d` は2桁。

| 値 | 意味 |
|---|---|
| `11` | 編集可能、表示状態 |
| `01` | 編集不可、表示状態（＝表示のみ） |
| `00` | 編集不可、非表示状態（＝非表示） |

10の位が2以上はプロテクト：2=編集不可プロテクト(変更可)、3=編集可能プロテクト(変更可)、
6=編集不可プロテクト(変更不可)、7=編集可能プロテクト(変更不可)。

**書込レイヤは状態値ではなく、ヘッダ部の値なし `lg*` / `ly*` で示される。**

調べようとしていた4状態の対応：非表示=`00` / 表示のみ=`01` / 編集可能=`11` /
書込=ヘッダの値なし行。

### 4-4. 外部変形では状態を書き戻せない（実証済み）

`JWW_SMPL.BAT` の読み込みデータ仕様では、`lg%x` / `ly%x` は
**書込レイヤグループ・書込レイヤの変更のみ**。状態を設定する記法は無い。

実機で確認した。Jw_cad へ次を返した：

```
lg0
ly2 00      ← レイヤ2を非表示にできるか
ly5
```

結果：書込レイヤは `lgf/ly0` → `lg0/ly5` に変わった（＝データは読まれている）が、
レイヤ2の状態は `11` のまま。**`ly2 00` は無視された。**

### 4-5. 復元は レイヤ設定ファイル(.JWL) で行う（`SAMPLE.JWL` より）

```
PRTCT_CH =  1
LAYCND_0 =[G],(0),(1),(2),...,(F)
LAYCND_1 =...
...
LAYCND_F =...
```

- 先頭がレイヤグループ自身の状態、続く16個が各レイヤ
- `100`以上 = 書込レイヤグループ／書込レイヤ
- 1の位：`0`=非表示 / `1`=表示のみ / `2`=編集可能
- 10の位：`1`=プロテクト(状態変更可) / `2`=プロテクト(状態変更不可)
- `PRTCT_CH = 1` でプロテクト状態も変更可能になる
- 行頭 `#` は注釈。`END` を行頭に書くとそれ以降は無視される
  （`SAMPLE.JWL` は2行目付近に `END` があるので読んでも何も起きない）

読み込み方：[設定]→[環境設定ファイル]→[読込み]→ファイルの種類を `*.JWL` にして選択。

**外部変形側と値の体系が違うので変換が必要**（`dump_layers.py` の `to_jwl()` が担当）：

| `#gn` | JWL |
|---|---|
| `11` 編集可能・表示 | `2` |
| `01` 編集不可・表示 | `1` |
| `00` 非表示 | `0` |
| プロテクト 10の位 2,3 | 10の位 `1` |
| プロテクト 10の位 6,7 | 10の位 `2` |
| 書込レイヤ／グループ | `100` |

### 4-6. 外部変形をキー一発で起動する（`Sample.jwf` より）

環境設定ファイルに登録すると `[Ctrl]+[A]`〜`[Z]` で外部変形番号100〜125を直接実行できる。


`[Ctrl]+[Shift]+[A]`〜`[Z]` は番号150〜175。

この設定はプロフィールに保存されないので、常用するなら `Jw_win.jwf` に書く必要がある。

**現在は適用していない**（一度入れたが元に戻した）。必要になったら上記1行を追記する。

## 8. ハマりどころ

- **`REM #jww` が無い bat は外部変形の一覧に出ない。** ファイルは存在しているのに
  選べない、という形で現れるので気づきにくい
- **`#g1` は `#h*` の直後**に書かないと無効（`JWW_SMPL.BAT` に明記されている）
- **`#cd` を使うと `jwc_temp.txt` の場所がずれる。** Jw_cad は自分が書き出した場所を
  読み直すので、返信は必ず読んだのと同じパスへ書くこと
- **256レイヤ揃わないときは `.JWL` を書いてはいけない。** 取れなかったグループを
  既定値で埋めてしまい、復元時に他グループの状態を破壊する
  （一度これで `LAYER_RESTORE.JWL` を壊した。現在はガード済み）
- **選択確定を押さないと bat は起動しない。** 「実行したのに出力が無い」の大半はこれ
- `jwc_temp.txt` は Shift_JIS(cp932)。bat も Shift_JIS + CRLF
- 図面全体を範囲選択すると `jwc_temp.txt` が巨大になる（対象図面は9.7MB）

## 10. 無操作での保存（`E_AUTOSAVE.bat`）— 2026-09-04 追加・**実機未検証**

6.5 の目印点案は不要になる可能性がある。範囲選択そのものを回避する道が見つかった。

### 発想

実証済みの事実3つを組み合わせる。

1. `#h4`（データ選択をしない）でも `#gn` があれば**書込レイヤグループの16レイヤは取れる**（B の結果）
2. 書き戻しで**書込レイヤグループの変更 `lg%x` は効く**（D の結果）
3. 書き戻しの `hr` で**同じ外部変形を再実行できる**（`JWW_SMPL.BAT`、および
   Version 2.23 の「外部変形の JWC_TEMP.TXT 内の h/****.BAT と hr を有効にした」）

→ グループを1つずつ移しながら16周すれば、**範囲選択なしで256レイヤが取れる。**

```
1周目  : 現在の書込グループの16レイヤを取得 → `lg<次>` + `hr` を返す
2〜16周: 同上
最終   : 出力とJWLを書き、`lg<元>` `ly<元>` を返して書込レイヤを元に戻す
```

ユーザー操作は「外部変形を起動する」だけ。`[Ctrl]+[A]` に登録すれば**1キーで完了**。

### 実装

- `E_AUTOSAVE.bat` … 制御行は `#jww` `#h4` `#gn` `#e`（`#g1` は選択が無いと無効なので不要）
- `loop_dump.py` … 巡回の制御。解析・出力・JWL生成は `dump_layers.py` を再利用
- 途中経過は `layerdump\_loop_state.json`。120秒より古い状態は破棄して最初からやり直す
- 無限ループ防止：訪問済み・試行済みのグループを記録、`MAX_ITER = 40` で打ち切り

疑似応答による16周シミュレーションで、256レイヤ取得・書込レイヤ復帰・JWL生成まで確認済み。
ただし**実機の Jw_cad では未検証**。

### 検証してほしいこと

1. `E_AUTOSAVE.bat` を実行して `he [LOOP] group=16 layer=256 OK` が出るか
2. 実行後、書込レイヤグループ・書込レイヤが元に戻っているか
3. 16周にかかる時間（python の起動が16回走る。数秒の見込み）

### ⚠️ 2026-09-04 実機テストで発覚した設計上のバグ(kamo指摘、重要)

13周でクラッシュした件とは別に、**そもそも`lg%x`(グループ自身の状態)の値が正しく
取れていない**ことが判明した。実機で以下を確認:

- ユーザーはグループ5〜7のいずれかを**グループ自体として**非表示にした記憶があった。
- しかし復元後、`_loop_state.json`の`gstates`は捕捉できたグループ(0〜c)すべてで`11`
  (編集可能)均一だった。グループ内の16レイヤの値(`ly%x`)は記憶通り正しく復元できていた
  (グループ6=表示のみ、グループ7=非表示など)ので、**レイヤ単位の読み取りは正しいが、
  グループ単位の読み取りだけがおかしい**。

**原因の仮説(kamo提示、有力)**: このメモの2026-08-27の記録に「入力(書込み)から外れた
レイヤは自動的に編集可状態に落ち着く」という実測済みの挙動がある。同じ仕組みが**グループ**
にも当てはまるなら、`loop_dump.py`が各グループを順番に「書込みグループ」に切り替える
(`lg%x`書き戻し)という手法そのものが、**切り替えた瞬間にそのグループ自身の状態を
編集可(`11`)にリセットしてしまっている**可能性が高い。つまり「読み取るために書込み対象に
切り替える」という操作自体が、読み取りたい値(グループの本来の状態)を破壊してしまう
自己矛盾がある。

レイヤ側の値が正しく読めているのは、グループを書込み対象にしてもグループ**内の各レイヤ**の
状態(表示/非表示/表示のみ)は書込みレイヤの選択とは独立して保持されるためと考えられる
(こちらは既存の`utils/line_attr_dialog.py`の知見とも整合する)。

**対策の方向性(未検証)**: グループNを書込み対象にする直前に、まだそのNが書込み対象で
なかった時点の`lg%x`の値を(他のグループがアクティブな状態から)読んでおく必要があるかも
しれない。例えば「グループNに切り替える直前の`jwc_temp.txt`に載っているlgN行の値」を
使う、切り替え前後で2回読む、などの方式変更が必要。次回`loop_dump.py`を直す際は、まず
グループを実際に非表示にした状態を作ってから、切り替え前後で`lg%x`の値がどう変化するかを
単体で検証すること。

## 11. 結論：`hr` ループ方式は破棄する（2026-09-04）

kamo が指摘した「グループ状態が全部 `11` になる」件は、**バグではなく方式そのものの欠陥**。
直せない。以下が根拠。

### なぜ起きるか

**書込レイヤグループは、定義上「編集可能・表示」でなければならない。**

- `SAMPLE.JWL`：「１の位にレイヤグループまたはレイヤの表示・編集状態を記述する。
  （**書込みレイヤグループまたはレイヤは除く**）」
  → 書込は状態指定の対象外。非表示の書込グループという状態は存在しない。
- `JWW_SMPL.BAT`：「書込レイヤグループの変更（プロテクトレイヤグループ・プロテクトレイヤは
  書込状態にできない）」
- 実測：巡回した13グループすべてが `11` 均一だった。

つまり `loop_dump.py` の「読むためにそのグループを書込に切り替える」という手段が、
**切り替えた瞬間に読みたい値を書き換えている。** 読み取り方法が観測対象を破壊している。

### これは読み取りエラーではなく、図面状態の破壊

さらに悪いことに、一度書込にしたグループは、書込から外れた後も `11`（編集可能）のまま残る。
つまり **`E_AUTOSAVE.bat` を実行すると、巡回したすべてのレイヤグループが
「編集可能・表示」に書き換えられる。** 保存しようとしている当の状態を消してしまう。

今回は実証用ファイルだったので実害は無かったが、**本番図面で実行すると
レイヤグループの表示状態がすべて失われる。**

### 修正案は成立しない

「切り替える直前の `lgN` の値を読む」案は使えない。`#h4` の出力には
**書込グループの `lg` 行しか出ない**（B の実測：groups=1）。他グループの状態は
そもそも出力されていないので、切り替え前に読むことができない。

全グループの `lg` 行が出るのは `#g1`＋実データ選択のときだけ。
それは `A_SAVE.bat` がやっていることで、その場合ループは不要。

### 対応

- **`E_AUTOSAVE.bat` と `loop_dump.py` は削除する。** 落ちるからではなく、壊すから。
- 保存は `A_SAVE.bat`（`#jww #h1 #g1 #gn`）が唯一の正しい方法。
  1回の実行で256レイヤとグループ状態を、**何も変えずに**取得できる。
- クラッシュ（iter 13→14）の原因は未特定のまま。方式を捨てるので追わない。

### 補足：この事故で学んだこと

`E_AUTOSAVE` を実行した図面のレイヤグループ状態は書き換わっている。
実行前の状態を記録した `matrix_*.csv` があれば、そこから `.JWL` を作って復元できる。

## 12. 無操作化の方針（10章を受けて）

復元側は解決済み（`WM_COMMAND` idCommand=32923 → 標準の「開く」ダイアログ →
`WM_SETTEXT` でパス投入 → `BM_CLICK`）。実機確認済み。

**同じ手法を保存側にも使えるはず。** 座標に依存しない経路がある：

1. `外部変形` コマンドを `WM_COMMAND` で送る（idCommand は未調査）
2. 開く「ファイル選択」ダイアログに `A_SAVE.bat` のパスを `WM_SETTEXT` → `BM_CLICK`

3. 範囲選択状態になったら、**コントロールバーの【全選択】ボタンを `BM_CLICK`**
4. **【選択確定】ボタンを `BM_CLICK`**（または `[Shift]+[V]` / `[Enter]` を送る）

### 検証してほしいこと

1. 外部変形コマンドの idCommand（Spy++ 等かメニュー列挙で取得）
2. 範囲選択中のコントロールバーの【全選択】【選択確定】が子ウィンドウとして取得でき、

3. 【全選択】だと図面全体が対象になりデータ量が大きくなる。重い場合は

## 14. 保存にかかる時間の調査（2026-09-07 開始・**測定待ち**）

### 症状

全選択方式でクリック一発になったが、保存完了まで
**軽い図面で約7秒、重い図面で約17秒**かかる（kamo報告）。

### 分かっていること（データから）

`layerdump\` に残っている `raw_*.txt` を全件確認したところ、
`jwc_temp.txt` は**最大でも約650KB**、直近の実行では 4KB〜122KB。
2MB超の間引き（`[NOTE] 元データ…`）が発動した形跡は無い。

この規模のデータを `dump_layers.py` が処理する時間を実データで計測したところ、
**読み込み・解析・出力の合計で約0.01秒**だった。

→ **17秒のほぼ全部が `dump_layers.py` の外側で消えている。**

### 最大の手がかり：軽い図面でも7秒

軽い図面でも7秒かかるということは、**データ量に依存しない固定費が5〜7秒ある**。
ここを潰せば重い図面も17秒から10秒台前半になる計算。

固定費の候補：

1. **`python.exe` の起動**（通常0.3秒程度。Windows Defender のスキャン、
   PATH解決の失敗、Microsoft Store スタブ経由などで数秒に膨らむことがある）
2. Jw_cad 側の外部変形の起動オーバーヘッド（コンソールウィンドウの生成など）

図面の重さに比例する部分の候補：

3. **Jw_cad の【全選択】と選択表示の再描画**（9.7MB の図面で全図形を選択）
4. Jw_cad が `jwc_temp.txt` を書き出す時間

### 次にやること：測定

推測で手を入れると切り分けが濁るので、**先に内訳を測る**。

`A_SAVE.BAT` と `dump_layers.py` に計測を仕込んだ版をチャットで渡してある

```
source: C:\jww\jwc_temp.txt
```

### 測定結果ごとの対策案（どれも未検証）

  読み直す前に終了する必要があるため、常駐側の完了を待つ同期の作り込みが要る

**Jw_cad の全選択・書き出しが重かった場合**

- `A_SAVE.BAT` に `REM #ht10` `#ht20` `#ht30` `#ht40` を追加する。

- 全選択をやめ、9章の【前範囲】で小さい範囲に戻す（操作は増える）

## 19. 18章の質問への回答（2026-09-08、cowork側）

### 副産物のほうが本題より大きな手がかりになっている

18章の「複数ウィンドウだと20.9秒、1つに整理したら7.3秒」という観測は、
本題の9秒を説明する鍵かもしれない。

**jw_cad のウィンドウが増えただけで13秒も悪化する**ということは、
遅延の正体が「jw_cad が外部変形を準備する処理」ではなく、
**ウィンドウの前面化・フォーカスの取り合い**にある可能性が高い。
外部変形の準備コストなら、ウィンドウ数が増えても倍増するような性質ではない。

JwNavigator は保存ボタンを押された時点でフォアグラウンドにいる。
`Ctrl+J` を jw_cad に届けるには、まず jw_cad を前面に出す必要がある。
Windows には `SetForegroundWindow` の制限（`ForegroundLockTimeout`）があり、
条件次第で前面化が拒否されたり、リトライやスリープを挟む実装になっていると
数秒単位で待つことがある。ウィンドウが複数あれば、その競合はさらに悪化する。

つまり **9秒は jw_cad の中ではなく、JwNavigator から jw_cad へ入力を届ける
経路にあるのではないか**、というのが新しい仮説。

### 回答1：他に思い当たる候補 → 「手で `Ctrl+J` を押して測る」

**次にやるのはこれ一つでいい。Defender 除外より先。**

手順：

1. jw_cad をクリックしてフォーカスを当てる（JwNavigator は介さない）
2. **自分の手で `Ctrl+J` を押す**
3. `log_MARK.txt` の1行目の時刻と、押した時刻を比べる

判定：

- **1〜2秒で起動した** → 9秒は jw_cad の中ではなく、**JwNavigator の送信経路
  （前面化・フォーカス処理）にある**。直せる可能性が高い
- **やはり9秒かかった** → jw_cad 内部の固定コストで確定。この方式では諦めてよい

リスクゼロ、所要5秒、しかも決定的。これまで
**「JwNavigator を経路から外して測る」という切り分けを一度もしていない**ので、
ここに9秒が隠れていても気づけない状態になっている。

### 回答2：「固定コスト」と結論づけるのはまだ早い

上の切り分けをしていないので、現時点では

- jw_cad 内部の固定コスト
- JwNavigator → jw_cad の入力経路のコスト

の**どちらか分からない**。18章は前者を前提に書かれているが、
20.9秒の観測は後者を示唆している。結論を出すのは回答1の測定後にしたい。

もし送信経路が原因だった場合の対処候補（未検証）：

- `AttachThreadInput` で入力キューを結合してから `SetForegroundWindow` を呼ぶ
  （前面化制限を正攻法で回避する定番手法）
- 前面化のリトライ間隔・スリープが実装に入っていないか確認する
- `keybd_event` ではなく、jw_cad のウィンドウへ直接 `WM_KEYDOWN`/`WM_KEYUP` を
  `PostMessage` する（前面化そのものが不要になる可能性。ただし
  ショートカット処理がキーボードフックやアクセラレータ経由だと届かないので要検証）

### 回答3：「bat は2回なのに cmd が4回開いて見える」

**心当たりは無い。断定できない。** ただ切り分け方はある。

現状 `log_A.txt` は先頭行が `>`（上書き）になっているので、
**同じ bat が2回走っても2回目が1回目を消してしまい、ログでは1回に見える。**
実行回数の証拠としては弱い。

確実にするなら、両方の bat の**1行目と最終行**に、共有の1ファイルへ
`>>`（追記）でマーカーを出す。

```bat
echo [MARK] %TIME% enter >> "%~dp0layerdump\trace.txt"
...
echo [MARK] %TIME% exit  >> "%~dp0layerdump\trace.txt"
```

- マーカーが4つ（enter/exit × 2）なら bat は2回。**窓4つは見た目だけ**
- マーカーが8つなら本当に4回走っている

あわせて、`py` へのフォールバック行の直前にも `echo [fallback]` を入れておくと、
`python` が失敗して `py` が走っている（＝1つの窓の中で2回起動している）
ケースを切り分けられる。

**なお、窓の非表示化について**：18章の「bat を起動しているのは jw_cad 自身なので
JwNavigator からは制御できない」という判断は正しいと思う。ただし
**bat の中身を差し替えることはできる**ので、実処理を
`pythonw.exe`（コンソールを持たない）や `start /min` に回せば、
少なくとも窓の点滅は減らせる可能性はある。機能的な問題ではないので優先度は低い。

### Defender 除外について

会社PCでセキュリティ設定に触るのは、判断が要るなら**やらなくてよい**と思う。
回答1の測定で送信経路が原因と分かれば、除外設定は不要になる。
順序としては 回答1 → （必要なら）Defender の順で。

**どちらも約13秒でほぼ差が無かった**。空きメモリ単体が直接の原因では
なさそうと判明。

**仮説B（jw_cad内部のundo履歴蓄積）**: 「毎回の保存で点作図→Escape
取り消しを繰り返しているので、jw_cad内部のundo履歴が積み上がって
処理が重くなっているのでは」（kamo発案）。検証として、**同じ重い図面を
一度全部閉じて新規に開き直し（undo履歴がまっさらな状態）、その直後の
最初の保存を計測**：

| 状況 | 時間 |
|---|---|
| 重い図面、今日何度も保存を繰り返した後（undo履歴が蓄積） | 19〜21秒 |
| **同じ重い図面を開き直した直後（undo履歴まっさら）** | **13.4秒** |

図面の重さ自体は同じはずなのに、開き直しただけで速くなった。
**「空きメモリ」より「undo履歴の蓄積」の方が有力な仮説**という結論に
至った。

**次にやること（未検証）**: この仮説が正しければ、`cleanup_mark_points()`
のEscapeによる後始末そのものが、繰り返すたびに重くなる原因を作っている
可能性がある（点作図＋取り消しの1往復ごとにundoスタックへ2エントリ
積むため）。長時間・多数回使うと保存がどんどん遅くなっていく現象が
無いか、今後の運用で観察すること。もし本当に問題になるなら、
「保存のたびに履歴を汚さない」代替の後始末方法（例：点を消さずに
許容する、または`図面の再読込み`等でundo履歴をリセットする定期的な
運用）を検討する必要がある。

## 21. 「4回cmd」の正体は本当に2周していた／前面化失敗による実害事故（2026-09-08）

### trace.txtで確定：1回の保存で本当に2周していた

19章の指摘を受けて`trace.txt`（追記式）で確認したところ、**1回のボタン
押下で`B_MARK`→`A_SAVE`のサイクルがまるごと2周していた**ことが確定した
（4回cmdが開くのは錯覚ではなく事実）。

切り分けとして、キー入力を一切送らず`Ctrl+J`だけを単体で押したところ
`B_MARK`は1回しか起動しなかった（`trace.txt`で確認）。**つまり原因は
`Ctrl+J`自体ではなく、後続で送っているキー入力（`0,0`Enter→`2,2`Enter）
の方にある**と判明した。有力仮説：終点の後の`Enter`が、外部変形終了後に
「Enter単独で直前のコマンドを繰り返す」仕様に引っかかり、`Ctrl+J`の
繰り返し実行を誘発している。

対策として、終点側を`Enter`無しでタイプし、代わりに9-1節の範囲確定専用
ショートカット`[Shift]+[V]`で確定するよう変更（`utils/layer_snapshot.py`）。
**この対策自体の効果はまだ実機で確認できていない**（下記事故のため中断）。

### ⚠️ 前面化失敗によりキー入力が別アプリ(VSCode)に漏洩する事故が発生

上記の対策を試した回、`SetForegroundWindow`（`AttachThreadInput`併用）が
失敗したにも関わらず、**それを無視してキー送信を続行する実装**になって
いたため、`Ctrl+J`・`0,0`・`2,2`・`Shift+V`の一連のキー入力が、その時点で
実際にフォアグラウンドだった**VSCodeへそのまま送られてしまった**
（kamo確認：jw_cad側にダイアログ等の反応は一切無し、VSCode側も実害は
無かったが、`Ctrl+J`はVSCodeの既定ショートカット「ターミナルパネル
表示切替」のため、他アプリの操作を誤発火させる実例となった）。

**`keybd_event`はハードウェアレベルのキー合成であり、送信先ウィンドウを
指定できない。** 前面化が実際に成功したことを確認しない限り、後続の
キー送信は絶対に行ってはならない、という設計上の欠陥だった。

**修正**: `trigger_save()`で`force_foreground(hwnd)`実行後、
`win32gui.GetForegroundWindow() != hwnd`なら**即座に中断し、以降のキー
送信を一切行わない**ように変更（`pending`として`None`を返す。呼び出し元の
`main.py`もエラーメッセージを更新済み）。**この安全対策は今後、
`keybd_event`を使うあらゆる自動化に適用する原則として扱うこと。**

## 22. 「2周する」問題の追加切り分けと最終判断（2026-09-08）

### `Shift+V`化では直らなかった

終点の`Enter`を`Shift+V`に置き換えても、`trace.txt`で確認したところ
**`MARK`→`SAVE`→`MARK`（2周目は`SAVE`まで進まない）というパターンで
やはり2回目が発生**した。「終点のEnterが直前コマンドを繰り返す」という
仮説は否定された。

### 連鎖なし（`Ctrl+J`→`A_SAVE`直結）なら1回だけ

`Ctrl+J`の割り付けを一時的に`B_MARK`ではなく`A_SAVE`直結に変更し
（連鎖・点作図なし）、同じキー入力を送ったところ、`trace.txt`に
**`SAVE`のenter/exitが1組だけ**記録され、8.6秒で完了した。
**これで「2周する原因は`h/A_SAVE.BAT`の連鎖の仕組み自体」と確定した。**
キー入力の内容、`Ctrl+J`自体、jw_cadの外部変形起動そのものはいずれも
無罪と判明している。

### 対策案「B_MARK/A_SAVEを別ホットキーに分ける」は断念

連鎖を使わず、`GCOM_100`(`Ctrl+J`=`B_MARK`)と`GCOM_110`(1番目=`Ctrl+K`
のはず=`A_SAVE`)を別々に登録し、JwNavigator側が`B_MARK`の完了
（`log_MARK.txt`更新）をポーリングしてから`A_SAVE`のキーを送る方式を
実装・試験した。

- `B_MARK`（`Ctrl+J`）は正常に起動した
- `A_SAVE`（`Ctrl+K`）が**起動しなかった**

`Sample.jwf`の仕様書を確認したところ、`GCOM_1XX`と実際のキー割り付けの
対応が、想定（`Ctrl+A`〜`Ctrl+Z`＝外部変形番号100〜125）と、仕様書内の
別の記述（`KEY_J`/`KEY_K`等は`[Shift]+文字`用の設定で、`Ctrl+`とは別物）
とで**食い違っていた**。`Ctrl+J`（`B_MARK`）は実機で確実に動き続けている
ので、jw_cadには両方の記述と矛盾しない何らかの内部規則があると思われるが、
**`Ctrl+K`が同じ規則で新規に割り付くとは限らない**ことが分かった。
この優先順位の正体は未解明のまま。

### 最終判断：連鎖ありに戻す（採用）

2ホットキー化は「重い起動コスト（約8〜9秒）を2回払うことになり、連鎖が
正常時より遅くなる」という速度面の懸念もあったため、`Ctrl+K`の謎を
これ以上追わず、**連鎖ありの方式（`B_MARK`→`h/A_SAVE.BAT`）に戻すことを
kamoと合意した**。「たまに2周して余分な点が作図され、保存が長くなる
ことがある」という既知の不具合は許容する。

- `Jw_win.jwf`/`kamo.JWF`: `GCOM_100`=`B_MARK`（元通り）、`GCOM_110`は
  空に戻した
- `mark_point.py`: `h/A_SAVE.BAT`連鎖を復活
- `utils/layer_snapshot.py`: `trigger_save()`を単一ホットキー版に戻した
  （前面化失敗時に中断する安全対策はそのまま維持）

### 次回もし再挑戦するなら

- `Ctrl+K`が実際にどのコマンド番号に紐づいているか（あるいは全く
  紐づいていないか）を、[設定]→[基本設定]→[KEY]タブのGUIで直接確認する
  のが一番確実（`Sample.jwf`の文書を読み解くより早い可能性がある）
- 連鎖自体が2周する根本原因（`jwc_temp.txt`の読み書きタイミング競合、
  `h/`ディレクティブの仕様上の癖等）を特定できれば、連鎖を活かしたまま
  直せる可能性がある
